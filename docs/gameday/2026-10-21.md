## Scenario 1 — blank page

**Hypothesis:** `site-down` fires in 7–15 minutes (check every 5 min, 2 failed periods in a row).

| UTC | Event |
|---|---|
| 07:02:22 | 70-byte `index.html` uploaded over the 45 KB page; CloudFront invalidated |
| 07:09:29 | `site-down` → ALARM (HTTP status was still **200**) |
| ~07:12 | Uptime log: `failed checks: site` → page problem, not API |
| 07:15:46 | Previous version copied back as latest; CloudFront invalidated |
| 07:19:29 | `site-down` → OK |

**What went well:** the uptime check looks for "Zihao Zhou" in the body, not only the status code — a status-only check would have stayed green. S3 versioning made the fix one command and kept the bad version as evidence.
**What went wrong:** the on-call engineer first took the *largest* version for the *latest*. The runbook did not say how to recognise the good version.

## Scenario 2 — Lambda loses its DynamoDB permission

**Hypothesis (runbook):** `lambda-errors` fires. **Hypothesis (reading the code):** it won't — the handler catches the exception and returns 503.

| UTC | Event |
|---|---|
| 07:30:37 | `PutRolePolicy` removes the DynamoDB statement (CloudTrail, user `zihao`) |
| 07:33:50 | `api-5xx` → ALARM |
| 07:39:29 | `site-down` → ALARM (`/health` returns 503) |
| ~07:41 | Lambda log: `AccessDeniedException ... dynamodb:GetItem`; CloudTrail shows who and when |
| 07:44:26 | Deploy re-run by hand (`workflow_dispatch`) |
| 07:45:33 | Terraform puts the reviewed policy back (1 change); `/health` ok |

**What went well:** layered alarms — the one we expected stayed silent, two others caught it. CloudTrail answered "who changed it". The fix was re-applying the code (IaC is the source of truth), not re-typing the policy.
**What went wrong:**
- `lambda-errors` cannot see handled exceptions, and the runbook said it would.
- The `api-5xx` runbook said `integrationStatus 200 + status 5xx` means "API Gateway itself". In reality it means "the Lambda ran and returned an error on purpose" — it would have sent the engineer to the AWS Health Dashboard instead of the Lambda log.

## Scenario 3 — data corruption (counter set to 0)

**Hypothesis:** no alarm fires; recovery needs point-in-time recovery (PITR).

| UTC | Event |
|---|---|
| 07:49:25 | `visitor_count` set to 0. All 5 alarms stay **OK** |
| 07:52:29 | PITR restore to 07:49:00 into a new table `visitors-restored` |
| ~07:57 | Restored table ACTIVE: backup = 586, live = 2 (visits after the damage) |
| ~07:59 | `ADD 586` run **twice** (first run looked stuck in the AWS CLI pager) → 1174 |
| 08:01 | `ADD -586` with a condition (`visitor_count >= 1172`) so it can only apply once → **588** ✅ |

**What went well:** PITR worked; the restore went to a new table, so the live table was never at risk. The engineer worked out the reconciliation rule unaided: **correct value = backup + visits since the damage**, done with an atomic `ADD` rather than read-then-write.
**What went wrong:**
- Nothing detects wrong data. Only a human would notice, possibly days later.
- `ADD` is not idempotent. A command that looks stuck gets run again → a second incident caused by the fix. Root cause: the AWS CLI pager (`(END)`).
- The runbook used `put-item <VALUE>`, which would have overwritten the visits made after the damage.

## Lessons (one line each)

- Check content, not just status codes: a 200 can be a broken page.
- An alarm you have never seen fire is a hypothesis, not a guarantee.
- Monitoring finds *broken*, not *wrong*. Backups exist for *wrong*.
- A backup is only real once you have restored from it.
- Recovery commands must be safe to run twice.
- Mitigate first, keep the evidence, then find the root cause.
